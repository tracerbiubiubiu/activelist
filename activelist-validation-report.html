五、发现与修正建议

F1 · 重要 AK/SK 验签基线修订未同步到 README 与 activelist 头部

ADR-003 于 2026-09-03 拍板「activelist 由零认证改为验 AK/SK HMAC 签名（utils aksk，M-A6 接线；用户侧零权限不变）」，implementation-plan M-A6 / §7 已同步；但 README.md:7「activelist 自身零认证」、activelist.md:20 最终画像「activelist 完全不管」、activelist.md:1447 §15.1「不做认证（且 §15 被标注继续有效）」仍为旧口径。

建议：统一为「用户侧零权限（不判定，zhuzhao 网关统一）；activelist 服务间验 AK/SK 签名（M-A6）」，同步修订 README 定位、activelist.md 头部与 §15 有效性标注。

F2 · 重要 脱敏口径自相矛盾（验收标准 vs 拍板）

已拍板「脱敏暂不做（风险接受 + schema sensitive 标记 + 统一日志出口两个钩子）」（ADR-003 审计落点、implementation-plan §1#7 / M-A6 / §7）；但 implementation-plan.md:32 验收项 A6 写「敏感值按规则脱敏」——A6 是 M-A 退出标准，直接与口径冲突；activelist.md:23「日志脱敏仍需」、README.md:34「脱敏」亦为旧表述。

建议：A6 改为「预留 sensitive 标记 + 统一日志出口，脱敏逻辑暂不实现」；README 第 34 行、activelist.md 最终画像同步为「脱敏暂不做（钩子预留）」。

F3 · 中等 activelist.md 收敛声明「§6.7–6.9 继续有效」与「整块砍掉 / 取代」并存

收敛声明第 8 行将 §6.7（查询安全）、§6.9（API）标为「继续有效」，但最终画像第 21 行说「§6.7 动态查询引擎整块砍掉」，implementation-plan §4 又说「API 清单取代 activelist.md §6.9 旧清单」。三处并存让读者无法单凭 activelist.md 判断实际口径。

建议：头部补一句「实现口径一律以 implementation-plan.md 为准，正文章节有效性标注仅表示概念层语义保留」，避免「继续有效」与「砍掉/取代」并列歧义。

F4 · 轻微 ADR-003 需求澄清节残留旧口径

ADR-003-integration-contract.md:90 仍写「activelist 零认证」「存储加密暂不需要 ⚠️」，未同步第 67 行 AK/SK 基线修订与第 117 行定稿补充后的口径（存储加密已拍板不做）。语义接近、无实质冲突。

建议：顺手更新该行（零认证→验签；存储加密→已拍板不做），与第 67 / 117 行一致。

R1 · 排期风险 E13（D2）未开始且阻塞联调与上线

activelist 零用户认证、无网关不能对外暴露；E13 反代 + SetForwardHeaders 目前为蓝图（🚦）。若 activelist 按计划完成 M-A6 而 E13 未排期，联调/上线将卡住。

建议：将 E13 纳入 zhuzhao 侧排期（哪怕靠后），并让 M-A6 交付前与 E13 就绪状态对齐；文档已标注「不阻塞开发、阻塞联调上线」，此点只需排期显式化。

R2 · 排期校准 总量 1.5–3 人日偏紧

六里程碑覆盖类型注册 / CRUD / Schema 演进 / 百万行流式导入与事务替换 / AK/SK 验签 / 多副本部署与备份，且验收含真实 PG 集成测试与门禁。1.5–3 人日（待校准）在含集成测试、多副本、备份前提下偏乐观，尤其导入与并发（lock_timeout / 幂等）部分。

建议：按里程碑拆算人日（建议 5–8 人日量级），或至少将「待校准」在启动前完成一轮校准，避免里程碑超支影响 Phase 3 主链节奏。
