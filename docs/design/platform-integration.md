## 1. 定位与数据写主

activelist 是本平台动态业务清单薄服务：类型/schema、数据 CRUD、revision、软删恢复和受控导入导出。每类型表及类型元数据由本服务写入；主仓拥有用户授权、使用清单的业务流程和业务审计。两仓不跨库改表，不把共享 PostgreSQL 技术栈理解为跨服务事务。

企业 SOC/SIEM、SOAR、CMDB、威胁情报、Agent/知识平台已存在，具体 API 合同待验证。资产权威属于 CMDB，风险/工单生命周期属于主仓，知识检索属于既有知识平台。activelist 既不是第二 CMDB，也不是风险数据库、原始事件湖、向量库或 Agent 配置仓。枚举继续使用主仓字典；从清单选值用授权查询/引用字段，不将清单复制成字典。

智能体可来自企业平台，也可为本平台特有能力的领域 Agent；两者查询 AL 都经主仓同一受权门面，不取得 AL 内部 SK 直连。模型只调用已有内网或获准外部 API，不因“查数据”新增推理部署或模型基础设施。

## 2. 当前保证和限制

- `TypeService.Register` 将类型元数据、DDL 和 schema 历史同事务提交；`Evolve` 用 metadata version 做 CAS。数据行未带 schema_version，按当前定义校验，破坏性演进不扫描改写全部旧行。
- `DataService.Update` 在事务中锁行、合并 patch 后全量校验并比较数据 revision。metadata version 与数据 revision 不是同一种版本；revision 不能由客户端自行加一。
- `DataService.checkUniqueDup` 先查再写，没有数据库硬唯一约束；并发同键可双写，缺少任一键会跳过查重，导入不检查业务 unique_fields。不能用“在事务内”推导并发原子唯一。
- `DataService.Import` 是锁表后全量替换，包含删除已有软删行；不是追加/upsert。同文件再次导入可能得到相同业务内容，但 revision 改变，不等于无副作用重放。
- 导出是含软删行的裸 JSON 数组，流中途失败可能只表现为截断；HTTP200 不能证明导出包完整。服务大导入通道与浏览器网关上限不同。
- 本服务只验服务 AK/SK，不做用户角色/行级权限。`sensitive` 目前只是存储标记，日志脱敏未启用，不能据字段存在声称已保护。

源码锚点：`internal/service/type_service.go` 的 `TypeService.Register` / `Evolve`，`internal/service/data_service.go` 的 `DataService.Update` / `checkUniqueDup` / `Import` / `Export`，`internal/meta/meta.go` 的 `Definition` / `Field`。准确现态和错误语义继续由[数据契约](../api/data-contract.md)维护。

## 3. R06：唯一性与 schema 演进，P7 承接

在 P7 开工前收口“应用软查重”和“严格唯一”两档的适用范围。严格档采用数据库原子约束或等价机制，先识别存量冲突，再明确缺失/null、字段类型、软删恢复、并发更新和导入的语义；不是给所有清单无条件追加硬索引。

schema 演进应有影响预检、兼容判断、迁移/修复方案与失败恢复。类型版本变化和在途旧定义写入的窗口要明确：继续允许的边界写成合同，需要收紧的与类型锁/版本校验同批实施。不能既允许破坏性变更，又把旧数据下一次写失败解释为“不需要迁移计划”。

实施涉及新索引/约束或数据迁移时，说明旧行清理、在线锁表影响、回滚与序列兼容。未选严格档的类型维持现有保证，并在类型合同中写清；不为此重造通用元数据平台。

## 4. R06：统一 IAM 下的查询与受控写能力

主仓提供类型、字段、行范围的业务查询 Port；浏览器、MCP、自然语言查询和两类 Agent 使用同一入口。服务身份只表示允许调用 AL，不能替代用户可见范围。X-Operator 用于签名归因，不根据 caller 提供的工号或组织字符串自行授予权限。

首批查询限定可查询类型、返回字段、现有过滤能力、分页/行数与时间预算；范围由主仓策略注入并验证。AL 当前仅有 q、单字段等值和 keyset 等合同，不假定已有任意排序、聚合或 SQL。需要扩展时先定白名单合同，禁止开放通用 text-to-SQL/内部数据库工具。

敏感字段先授权再脱敏，日志和导出适用同一数据分类。受限列、被删除对象和无权对象存在性不得通过查询建议、计数、错误或模型上下文泄漏。若某清单没有可执行的行权限，只向明确获准的角色开放或提供受权深链，不能用模型提示代替隔离。

由外部知识服务消费数据时，只推获准字段/范围与来源版本，核验其删除/撤权/缓存合同；默认不把全部 AL 数据复制进知识库。R06 的受权视图是首个 AL 自然语言查数场景的前置，不因任务计划在 P7 就允许 P6 提前绕过。

### 定时任务和统一调用门面

核心与可插拔模块使用同一受权能力门面，AL业务查询和写入均登记稳定`capability_id`与`contract_version`；对外提供可授权的HTTP/API合同，MCP仅适配同一能力，不另写一套读写。统一是合同与执行入口一致，不强制主仓内部同域短事务绕HTTP或全部排入TR。

定时任务通过TR唯一业务调度主，触发主仓获准的AL操作能力；主仓执行当前主体/持续grant、类型/行/字段允许集、操作风险和版本检查后，以受限服务身份调用AL公开接口，由AL提交自己的事务。`actor`、`dept`、`X-Operator`仅归因或标签，不单独授予权限；TR、浏览器和Agent均不直写AL库，也不由模型持内部SK直连。

首批写入选择现有插入/patch/软删/恢复中的代表操作，按操作定义预期revision、白名单字段和稳定业务效果键。目标写主AL须将效果去重凭证与实际数据效果原子提交，主仓持调用/交接收据；不能只靠主仓去重挡住响应丢失后的重复写。写冲突不静默重读后覆盖别人修改；重复操作凭已提交receipt返回原效果，未知先对账。当前API尚无这套效果去重合同，不能据现有CRUD宣称链已成立。需要追加/upsert时必须新增受审合同，现有全量`Import`不能冒充patch或自动同步捷径。数据提交、业务效果与结果回贴分开记账，跨仓不假设同事务。

## 5. R06：导入、导出与可靠交接

全量 replace 是高风险运维动作，首批 AI/MCP 不直接暴露。后续如确有业务需求，预检应绑定目标、模式、文件校验和、行数、影响与目标基线，经过精确确认后执行；权限或基线改变须重新校验。追加/upsert 是新合同，不能更名现有 import 冒充兼容。

导出/迁移包的完整性与恢复需有校验和、manifest 或等价证据，失败不能留下看似完整的成功文件。恢复在独立库验证，包含 revision sequence 和旧缓存失效；备份同盘副本不自动等于灾备。

**CMP-R02的特定承接**：P7/R06先核当前main，不把旧比较报告中的运行缺陷直接当今天仍未修。必须保留以下独立反例：解析完整消费至EOF，尾随垃圾/第二个顶层JSON值拒绝且不提交部分替换；合法文件末尾空白可接受。全量replace后，任何旧revision/ETag/乐观锁令牌不可因ID/序列从头复用而重新有效，须选择单调修订序列或明确collection generation，令牌带世代验证；不能只测普通Update CAS。

导入预算按网关、服务body、解析后的行/字段、解压（如支持）、临时磁盘/文件、锁/事务时长分别列上限与失败清理。现有主仓1MiB网关与AL直连16MiB通道的差异须明确适用调用方，不能只把某层上限调大；业务导入不能绕网关用内部SK提权。测试需覆盖截断、边界超限、临时盘不足/中断、替换失败恢复旧集与旧令牌失效。已修子项保留源码/回归收据，未修在R06实施；主仓D05工单配置包导入不替代这里的运行数据验收。

AL不建设第二事件总线，也不因触发任务而依赖TR；但“AL不感知事件”不能解释成数据写主不提供变更事实。**AL在本库写事务内记录最小变更凭证/outbox，或提供有完整性与恢复证明的变更feed；主仓拥有统一订阅、路由、权限及任务触发决策。** 仅在主仓网关收到成功后补发事件会漏掉直接服务写、异步任务写、崩溃和导入路径；扫描当前数据也不能恢复被replace或删除的历史变化。

该补充校准[旧ADR-003](../adr/adr-003-integration-contract.md)的D4“AL不感知事件”表述：旧ADR保留历史，不据其句子取消本轮源事实目标。改变的是最小事实生产边界，不是给AL移入平台IAM、流程决策或独立消息基础设施。两服务提交失败、审计/凭证失败、已成功但响应丢失分别对账，不假定统一事务或端到端exactly-once。

### AL写主的最小变更事实

以下均为目标，当前源码没有outbox或变化订阅接口。`DataService.Insert`、`Update`、`SoftDelete`、`Restore`、`Import`是必须逐路径核对的产品写入口；定时任务也经同一用例提交，不能只给浏览器路径加事件。类型/schema变更是独立元数据事实，具体事件和已有`TypeService.Register/Evolve/Deprecate`的对应关系在启用前冻结，不混成文档内容变更。绕过这些受控入口的DB运维修复/迁移须有专门批次manifest或重建对账，不默认被产品事件捕获。

- **原子边界**：已启用的可靠变更源，数据事实、最小变更凭证、该入口的领域约束及效果去重凭证同一个AL事务提交；必需凭证失败不返回该源变更已可靠交接。AL只持久记录事实，提交后才投递或供拉取，不在数据事务里等待主仓/TR的网络响应。
- **事实信封**：稳定`event_id`、事件schema版本、生产者/来源实例与数据世代、类型/文档ID、已提交revision、操作类别、发生时间、最小变更字段/摘要或受权引用、`correlation_id/causation_id`。metadata version、数据revision、能力合同版本及投递游标各自独立。
- **单条与批次**：普通写记录对应文档的变化；`Import`默认记录有界replace批次/完成事实，带类型/世代、范围、水位、数量及校验信息或可恢复manifest引用。默认不把一次大导入展开为无限逐行任务；确需逐行订阅时另定有界分片、历史数据来源与预算后启用。不能在提交后仅读当前表来伪造导入前后完整diff。
- **提交顺序**：当前全库revision序列可跳号，且分配顺序不能证明跨事务提交顺序。不能简单用`max(revision)`推进消费者游标。feed必须有可核验的提交完整性/批次结束及可恢复checkpoint，或者按持久outbox逐条确认；删除/replace也要保留必要事实，不能因旧行消失就当没有变化。
- **数据最小化**：事件默认不含整行前后快照、敏感字段或凭据。消费者查详情时仍重新授权；仅有事件引用不授予读权。需要历史快照的场景须明确可用性、字段范围和保留政策，不用当前值冒充历史事实。

### 可靠交接、统一ID与订阅反应

主仓接收端先持久登记收件/重复判定，再确认AL投递；“平台已收件”不等于“任务完成”。一条数据流选择明确的push或pull交接主；不同跳的checkpoint分别归其所有者，不让两个未协调的poller各自推进。AL relay可多副本认领，但稳定事件ID不变、租约/fence和失败可恢复；重复传输由接收端去重，不把签名时间窗当业务幂等。首期不要求额外搭建MQ产品，已有受控HTTP/feed可以承载。

| 标识 | 用途 |
|---|---|
| `capability_id` + `contract_version` | 稳定能力和静态合同版本；用于目录/调用校验 |
| OpenAPI `operationId` | API操作别名，与能力有受控映射；不是每次执行的新ID |
| `operation_id` | 跨重试保持的业务效果身份；同键不同目标/输入拒绝 |
| `invocation_id` | 一次逻辑调用身份，同一调用重投不重置；不是每次HTTP请求号 |
| `delivery_id` | 一次投递尝试身份，每次重投可新建 |
| `event_id` | 已提交源事实身份，回放同一事实不换号 |

现有`action`、`action_id`及回调wire先由版本化adapter映射，不因统一命名在本轮直接改协议。主仓按订阅ID/订阅版本/来源/`event_id`/反应序号登记消费和反应意图，为其目标逻辑调用及业务效果生成稳定身份；重投重用，显式重新执行须有新操作及原因，不靠换投递ID绕过幂等。能力发现、事件订阅配置或收到消息均不自动授执行权，目标操作仍按当前主体/资源范围及持续授权复验。

源数据变更事件、执行命令和结果交付是三种语义：AL陈述已发生事实，主仓将获准反应落为意图，TR执行有界任务，结果再交给有权的消费者展示或写回；不能让AL在事件事务里直接跑任务，也不能把TR的执行回调误当结果通知。来源任务更新AL产生的新事实保留因果关系，不一律丢弃“任务来源”事件。

### no-op、防回环与预算

当前`Update`即使业务值相同也可能产生新revision；本轮不修改该API行为。目标事件明确`data_changed`及业务字段变化，默认数据订阅只响应真正业务差异，不把`updated_at/updated_by`自动变化当重复触发理由。需要监听技术写入、软删恢复或元数据变化时使用明确事件类别及规则。重复投递不是新业务变化；重复导入的批次事实也不自动授权逐行重跑。

订阅规则在主仓管理，绑定事件/字段谓词、目标能力版本、允许输入映射和授权主体。配置预检识别明显循环；运行时保留root/cause和有界链深、同根反应次数、对象并发/开始速率/扇出预算。AL更新→任务→AL更新达到预算时持久hold并暴露原因、待处置对象及恢复入口，不能静默丢事件或无限自触发。人工恢复同一回合不得暗中重置预算；调用方不能用自填新root规避预算，需要新根重跑时显式批准并关联旧链。

并发更新继续用revision/CAS和领域幂等；同一对象的有序需求按类型/对象分区或受控串行，不要求所有AL类型全局FIFO。慢消费者、重放风暴、限流/退避、毒消息隔离、积压水位与保留预算须有可见状态；限额和超限处置在代表链详设时冻结，当前不编造全平台吞吐SLA。

## 6. 验收、运行与排期边界

R06 统一承接并发唯一、schema/存量兼容、授权查询、敏感字段、导入完整性与恢复，和主仓 I01/I02 的调用/身份合同协同。决定窗口为 P7 开工前，实施与关闭在主总账 R06 中维护；安全约束若先被新消费方触发，必须先完成相应前置，不能带已知旁路上线。

长期保留大量合成 mock 与故障数据：schema 新旧版本、同键并发、缺失/null、软删恢复、存量冲突、导入中途失败、过期基线、重复确认、分页边界、跨组织/类型/字段撤权、日志敏感值与导出截断。mock 可验证业务场景和 UI，不能证明数据库硬约束或真实授权正确。

新增互通验收还须覆盖：五类产品写入口均产生可恢复源事实；业务提交后kill、投递ACK前kill、重复/迟到/乱序、no-op、replace部分失败和大批次预算；回写回环被有界hold；撤权后既有订阅/任务不放行；事件收件成功但任务失败仍可对账。多副本启用前再验发布认领/fence与重复消费者，首期单实例不提前建设HA。

contract 层验证主仓查询 Port、服务签名、字段/schema 与错误兼容；真实 PostgreSQL 层验证并发、DDL/事务、序列与恢复；真实专业接口和企业 IAM 环境单独留证。各层独立登记，外部尚不可达不阻塞 mock/contract，也不能据前两层关闭 real。

本页没有实施R06或新增源事件/订阅链，也没有修改API、迁移、依赖或执行运行验收。AL变更源、受控写adapter和订阅触发属于新增能力互通范围，P7实施前须单列子交付/验收和增量复估；不自动包含在原R06 5–8日、I01或已冻结排期里。代表链首先证明“定时任务→AL受控更新”和“AL变更→一次获准任务”，再逐步扩展；复杂分支/长等待仍按平台后继窗口，不先建通用DAG。后续代码批同步[数据契约](../api/data-contract.md)、[运维](../ops/README.md)和主总账，仍按正常门禁验证。
