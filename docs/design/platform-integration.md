# 平台集成、数据安全与演进合同

> 2026-11-11 重规划。当前行为仍以[当前设计](overview.md)、[HTTP](../api/contract.md)和[数据契约](../api/data-contract.md)为准；本文描述后续承接，不宣称新增能力已实现。排期、工作量和关闭证据唯一登记在主仓[规划总账](../../../zhuzhao/docs/review/planning-backlog.md)的 **R06 / P7**，本仓不另起估算。

## 1. 定位与数据写主

activelist 是本平台动态业务清单薄服务：类型/schema、数据 CRUD、revision、软删恢复和受控导入导出。每类型表及类型元数据由本服务写入；主仓拥有用户授权、使用清单的业务流程和业务审计。两仓不跨库改表，不把共享 PostgreSQL 技术栈理解为跨服务事务。

企业 SOC/SIEM、SOAR、CMDB、威胁情报、Agent/知识平台已存在，具体 API 合同待验证。资产权威属于 CMDB，风险/工单生命周期属于主仓，知识检索属于既有知识平台。activelist 既不是第二 CMDB，也不是风险数据库、原始事件湖、向量库或 Agent 配置仓。枚举继续使用主仓字典；从清单选值用授权查询/引用字段，不将清单复制成字典。

智能体可来自企业平台，也可为本平台特有能力的领域 Agent；两者查询 AL 都经主仓同一受权门面，不取得 AL 内部 SK 直连。模型只调用已有内网或获准外部 API，不因“查数据”新增推理部署或模型基础设施。

## 2. 当前保证和限制

- `TypeService.Register` 将类型元数据、DDL 和 schema 历史同事务提交；`Evolve` 用 metadata version 做 CAS。数据行未带 schema_version，按当前定义校验，破坏性演进不扫描改写全部旧行。
- `DataService.Update` 在事务中锁行、合并 patch 后全量校验并比较数据 revision。metadata version 与数据 revision 不是同一种版本；revision 不能由客户端自行加一。
- `DataService.checkUniqueDup` 先查再写，没有数据库硬唯一约束；并发同键可双写，缺少任一键会跳过查重，导入不检查业务 unique_fields。不能用“在事务内”推导并发原子唯一。
- `DataService.Import` 是锁表后全量替换，包含删除已有软删行；不是追加/upsert。同文件再次导入可能得到相同业务内容，但 revision 改变，不等于无副作用重放。
- 导出是含软删行的裸 JSON 数组，流中途失败可能只表现为截断；HTTP200 不能证明导出包完整。服务大导入通道与浏览器网关上限不同。
- 本服务只验服务 AK/SK，不做用户角色/行级权限。`sensitive` 目前只是存储标记，日志脱敏未启用，不能据字段存在声称已保护。

源码锚点：`internal/service/type_service.go` 的 `TypeService.Register` / `Evolve`，`internal/service/data_service.go` 的 `DataService.Update` / `checkUniqueDup` / `Import` / `Export`，`internal/meta/meta.go` 的 `Definition` / `Field`。准确现态和错误语义继续由[数据契约](../api/data-contract.md)维护。

## 3. R06：唯一性与 schema 演进，P7 承接

在 P7 开工前收口“应用软查重”和“严格唯一”两档的适用范围。严格档采用数据库原子约束或等价机制，先识别存量冲突，再明确缺失/null、字段类型、软删恢复、并发更新和导入的语义；不是给所有清单无条件追加硬索引。

schema 演进应有影响预检、兼容判断、迁移/修复方案与失败恢复。类型版本变化和在途旧定义写入的窗口要明确：继续允许的边界写成合同，需要收紧的与类型锁/版本校验同批实施。不能既允许破坏性变更，又把旧数据下一次写失败解释为“不需要迁移计划”。

实施涉及新索引/约束或数据迁移时，说明旧行清理、在线锁表影响、回滚与序列兼容。未选严格档的类型维持现有保证，并在类型合同中写清；不为此重造通用元数据平台。

## 4. R06：统一 IAM 下的授权查询

主仓提供类型、字段、行范围的业务查询 Port；浏览器、MCP、自然语言查询和两类 Agent 使用同一入口。服务身份只表示允许调用 AL，不能替代用户可见范围。X-Operator 用于签名归因，不根据 caller 提供的工号或组织字符串自行授予权限。

首批查询限定可查询类型、返回字段、现有过滤能力、分页/行数与时间预算；范围由主仓策略注入并验证。AL 当前仅有 q、单字段等值和 keyset 等合同，不假定已有任意排序、聚合或 SQL。需要扩展时先定白名单合同，禁止开放通用 text-to-SQL/内部数据库工具。

敏感字段先授权再脱敏，日志和导出适用同一数据分类。受限列、被删除对象和无权对象存在性不得通过查询建议、计数、错误或模型上下文泄漏。若某清单没有可执行的行权限，只向明确获准的角色开放或提供受权深链，不能用模型提示代替隔离。

由外部知识服务消费数据时，只推获准字段/范围与来源版本，核验其删除/撤权/缓存合同；默认不把全部 AL 数据复制进知识库。R06 的受权视图是首个 AL 自然语言查数场景的前置，不因任务计划在 P7 就允许 P6 提前绕过。

## 5. R06：导入、导出与可靠交接

全量 replace 是高风险运维动作，首批 AI/MCP 不直接暴露。后续如确有业务需求，预检应绑定目标、模式、文件校验和、行数、影响与目标基线，经过精确确认后执行；权限或基线改变须重新校验。追加/upsert 是新合同，不能更名现有 import 冒充兼容。

导出/迁移包的完整性与恢复需有校验和、manifest 或等价证据，失败不能留下看似完整的成功文件。恢复在独立库验证，包含 revision sequence 和旧缓存失效；备份同盘副本不自动等于灾备。

AL 不新增独立领域事件总线。清单修改需要触发工单/任务时，业务属主记录可靠意图与幂等交接；AL 保留数据写主。两服务提交失败、审计失败、已成功但响应丢失分别对账，不假定统一事务或端到端 exactly-once。

## 6. 验收、运行与排期边界

R06 统一承接并发唯一、schema/存量兼容、授权查询、敏感字段、导入完整性与恢复，和主仓 I01/I02 的调用/身份合同协同。决定窗口为 P7 开工前，实施与关闭在主总账 R06 中维护；安全约束若先被新消费方触发，必须先完成相应前置，不能带已知旁路上线。

长期保留大量合成 mock 与故障数据：schema 新旧版本、同键并发、缺失/null、软删恢复、存量冲突、导入中途失败、过期基线、重复确认、分页边界、跨组织/类型/字段撤权、日志敏感值与导出截断。mock 可验证业务场景和 UI，不能证明数据库硬约束或真实授权正确。

contract 层验证主仓查询 Port、服务签名、字段/schema 与错误兼容；真实 PostgreSQL 层验证并发、DDL/事务、序列与恢复；真实专业接口和企业 IAM 环境单独留证。各层独立登记，外部尚不可达不阻塞 mock/contract，也不能据前两层关闭 real。
